# LLM Wiki 運用手順

**このファイルは「いつ何を実行するか」を定める。** ページの規約（frontmatter・命名・置き場所の基準）は [SCHEMA.md](SCHEMA.md) が正。役割を混ぜないこと。

---

## 1. 平常運転（この4つだけ）

| いつ | コマンド | 目安 |
|---|---|---|
| 作業を始めるとき | `/llm-wiki query 今の状況と次にやることは？` | 10秒 |
| 作業の区切り | `/llm-wiki ingest 今日の作業内容` | 5〜10分 |
| ingest の直後 | `git diff docs/wiki` で差分レビュー | 5分 |
| 週1回（金曜など） | `/llm-wiki lint` → 裁定 | 15〜30分 |

**人間の負荷は週30〜60分。** これを払えないなら、入れるソースを絞るか導入を見送る。

---

## 2. 作業開始時 — query

```
/llm-wiki query 今の状況と次にやることは？
/llm-wiki query 認証まわりの設計はどうなっている？
```

`index.md` → 関連ページの順に読んで答える。コードベース探索が走らないので数秒で返る。

- 回答には**必ずページ名が引用される**（`<project>-open-issues.md より`）。引用がなければ Wiki を読んでいないので指摘する
- Wiki に無ければ「Wiki に無い」と明言してから調べる。**推測で埋めさせない**
- 調べた結果に再利用価値があれば、書き戻しを提案させる

---

## 3. 作業の区切り — ingest

```
/llm-wiki ingest 今日の作業内容
/llm-wiki ingest docs/raw/2026-01-15-api-docs.md
/llm-wiki ingest https://example.com/article
```

会話を取り込む場合は `docs/raw/YYYY-MM-DD-<topic>.md` に固定してから取り込む。**raw に置いたファイルは以後書き換えない。**

### 人間がやること: ソースを選ぶ

ここで質が決まる。**入れないものを決める仕事**。

- 会話ログを丸ごと入れると、試行錯誤の過程まで載って薄まる
- 結論だけ入れると、なぜそうなったかが消えて後で判断できなくなる
- 判断基準は「**次に同じ場面に来た人が踏む罠かどうか**」

> 実例: `fly launch` で失敗して `apps create` に切り替えた経緯は、結果だけ書くと次に同じ罠を踏むため過程ごと残した。

### 正常な ingest の目安

**1ソースで複数ページに波及する。** 1ページしか触っていないなら取り込みが浅いので指摘する。

---

## 4. ingest の直後 — 差分レビュー（最重要）

```sh
git diff docs/wiki
```

**見るのは3点だけ。**

| 観点 | 何を確かめるか |
|---|---|
| **訂正の妥当性** | 古い記述を上書きした箇所。本当に前が誤りか、単に状況が違うだけか。素通しすると「最後に喋った人が勝つ」Wiki になる |
| **confidence の格付け** | LLM は放っておくと未検証も断定調で書く。「実機で確認した / 仕様上そうなるはず / たぶん」を区別する |
| **機密の混入** | API キー、アカウント情報、`docs/local/` の内容が複製されていないか |

指摘はその場で口頭指示でよい。

```
<project>-deployment.md の◯◯の記述、実機未確認だから confidence: low にして
```

---

## 5. 週1回 — lint

```
/llm-wiki lint
```

**lint は検出を報告するだけで自動修正しない。** 直すものを人間が選ぶ。

| 検出項目 | 人間の判断 |
|---|---|
| 矛盾 | どちらが正しいか決める（任せると機械的に新しい方を採る） |
| リンク切れ | 「次に書くべきページ」の候補。**全部書かず、書く価値があるものを選ぶ** |
| 孤立ページ | リンクを張るか、不要なので消すか |
| 陳腐化 | 更新するか、「もう触らない」と決めて閉じるか |
| 出典なし | 出典を補うか、記述ごと削るか |
| 昇格候補 | プロジェクト固有か、`~/wiki/knowledge/` に上げるか |

指示は一括でよい。

```
矛盾1と3を直して。リンク切れは <project>-session-recovery だけ書いて
```

修正したら `log.md` に追記されることを確認する。

## 6. 新しいプロジェクトを接続する（初回のみ）

```sh
cd ~/development/<project>
mkdir -p docs/raw docs/wiki
ln -sfn ~/development/<project>/docs/wiki ~/wiki/mounts/<project>
```

続けて Claude に依頼する。

```
このプロジェクトを LLM Wiki に接続して。CLAUDE.md を作って ~/wiki/projects/<project>.md も。
そのあと README を ingest して
```

最後に git 追跡へ加える。**`git diff docs/wiki` でのレビュー手順が回らなくなるため、追跡は必須。**

```sh
echo "docs/local/" >> .gitignore   # ローカル専用メモがある場合
git add .gitignore docs/raw docs/wiki CLAUDE.md
git commit -m "LLM Wiki を導入"
```

### 接続する価値がある対象

- ◯ 数週間以上触り続ける / セッションを跨ぐ / 全体を把握しておきたい
- ✗ 一度きりの調べ物、休眠プロジェクト → `~/wiki/index.md` に名前を並べるだけでよい

---

## 7. 人間にしかできない4つ

自動化を検討するときの線引き。

1. **何を入れないか** — 入力の選別
2. **どちらが正しいか** — 矛盾の裁定
3. **どこまで確かか** — confidence の格付け
4. **何を書かないか** — 機密の線引き

いずれも「正解が資料の中にない」判断。逆に**要約・リンク張り・整形・検出は全部 LLM 側**に置ける。

---

## 8. 負荷を下げる

- **lint を週次 cron / GitHub Actions に載せ、検出結果を Issue にする** — 実行忘れがなくなる
- **入れるソースを絞る** — 週1回、セッション末に「今週の決定事項」だけでも機能する
- **SCHEMA.md をテンプレとして効かせる** — 毎回「どう書く？」を考えない
- **チーム運用では ingest 実行者を1人（または CI）に固定する** — 他メンバーは `raw/` に積むだけ。レビュー品質が安定し、コンフリクトも減る

---

## 9. やってはいけない

- **lint を回さない** — 数ヶ月で「古いメモ置き場」に劣化する。lint は保守作業ではなく、Wiki が同じ誤りを繰り返す特性への対価
- **差分レビューを飛ばす** — 誤りが書き込まれると、以後**毎回同じ誤りを自信満々に答える**
- **API キー・トークンを書く** — 「`.env` に設定済み」とだけ書く
- **git 未追跡ファイルの内容を複製する** — 参照先として名前を挙げるに留める
- **LLM の書き込みを直接 main に入れる（チーム時）** — 必ず PR レビューを通す
- **破壊的な整理を commit なしで実行する** — すべて可逆に

---

## 10. トラブル対応

| 症状 | 対処 |
|---|---|
| query の回答にページ名の引用がない | Wiki を読んでいない。`index.md` から読むよう指示する |
| ingest が1ページしか触らない | 取り込みが浅い。既存ページとの関連を洗うよう指示する |
| 同じ知見が複数プロジェクトに重複 | `~/wiki/knowledge/` へ昇格させ、各所からリンクに置き換える |
| ページが増えて全体が見えない | `~/wiki` を Obsidian の vault として開く。mounts 経由で各プロジェクトも横断表示される |
| Wiki の記述が実装とズレている | 実装が正。Wiki を直し、`log.md` に訂正として残す |
