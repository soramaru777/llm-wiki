# 6. よくある質問

---

## 導入前の疑問

### Obsidian は必要ですか？

**必要ありません。** AI は Obsidian を一切使わず、Markdown ファイルを直接読み書きします。Obsidian は**人間が眺めるためのビューア**にすぎません。

ただし多くの人が併用しています。理由は、

- `[[リンク]]` を辿れる／逆リンクが見える
- グラフビューで Wiki の形が見える（Karpathy 本人も推奨）
- `Dataview` プラグインで frontmatter に対してクエリが書ける

代替としては、VS Code（Foam 拡張など）、GitHub 上でそのまま閲覧、あるいは何も使わない（`index.md` があれば実は困らない）。

**おすすめは「まず入れずに始めて、ページが50を超えて全体が見えなくなったら入れる」**です。後から乗せるだけなので急ぐ必要はありません。

### ベクトルDBや埋め込みは要りますか？

**要りません。** 実体は素の Markdown フォルダなので、テキストエディタと AI エージェントだけで完結します。これが RAG との大きな違いです。

### RAG より優れているのですか？

用途が違います。

- **同じ対象に何度も聞く** → LLM Wiki
- **大量の文書から都度1件を探す**（過去の契約書、問い合わせ履歴など） → RAG
- **一度読んで終わり** → どちらも不要。そのまま AI に読ませるのが最速・最安

### コストはどれくらいですか？

**取り込みが高く、質問が安い**構造です。1回の取り込みで複数ページを書き換えるため出力トークンを多く使いますが、質問時は数ページ読むだけで済みます。

損益分岐は「**同じ資料に何度も聞くか**」。一度きりなら取り込む意味はありません。

### どれくらい手間がかかりますか？

**週30〜60分**が目安です。内訳は、取り込み結果のレビュー（5分 × 回数）と週1回の lint（15〜30分）。

重ければ**取り込むソースを絞ってください**。負荷は取り込み量にほぼ比例します。週1回「今週の決定事項」だけでも機能します。

## 運用中の疑問

### 何を取り込めばいいか分かりません

最初は `README.md` だけで構いません。慣れてきたら次を足します。

- 設計を決めたときの会話
- ハマって解決したときの経緯（**過程ごと**残す）
- 読んで役立った外部記事

逆に**入れないほうがいいもの**は、試行錯誤しただけで結論の出ていない会話、一度きりの調べ物、コードを読めば分かること。

### 取り込んだのに1ページしか変わりません

取り込みが浅い状態です。こう指示してください。

```
既存ページとの関連をもっと洗って。関係するページを全部更新して
```

正常なら**1つの資料で複数ページが書き換わります**。

### 回答にページ名の引用がありません

Wiki を読んでいない可能性が高いです。

1. `CLAUDE.md` に「作業を始める前に `docs/wiki/index.md` を読むこと」と明記する
2. その場では「`index.md` から読んで」と指示し直す

### Wiki の記述が実装とズレています

**実装が正です。** Wiki を直し、`log.md` に訂正として残します。

「なぜズレたか」も併せて書いておくと、同じズレを繰り返しにくくなります。

### ページが増えて全体が見えません

3つの手があります。

1. `index.md` を整理する（カテゴリ分け、1行要約の見直し）
2. `~/wiki` を Obsidian の vault として開く（mounts 経由で全プロジェクトが見える）
3. lint の「孤立ページ」を見て、要らないページを消す

### 同じ知識が複数プロジェクトに重複しています

`~/wiki/knowledge/` へ**昇格**させ、各プロジェクトからはリンクに置き換えます。lint が昇格候補として検出してくれます。

### 誤った情報が書き込まれてしまいました

該当ページを直せば、**次回から確実に直った内容が返ります**。これが RAG に対する Wiki の利点です。

再発防止としては、取り込み直後の `git diff docs/wiki` を習慣にしてください。

### lint を回す時間がありません

**優先度を付けるなら、差分レビュー > lint** です。差分レビューは誤りが定着する前に止められるので、こちらのほうが効果が高い。

lint は GitHub Actions の週次 cron に載せ、検出結果を Issue にすると忘れなくなります。

### API キーが書かれていました

すぐ消してください。そのうえで、

- `SCHEMA.md` に「機密を書かない。`.env` に設定済みとだけ書く」と明記する
- 取り込み直後のレビューで毎回チェックする

すでにコミットしてしまっている場合は、キー自体を再発行するのが確実です。

## git と公開範囲

### `docs/wiki/` と `docs/raw/` は git にコミットすべきですか？

**wiki は追跡し、raw は追跡しません。**インストーラの `--connect` がこの設定を自動で入れます。

| | 追跡 | 理由 |
|---|---|---|
| `docs/wiki/` | **する** | 差分レビュー（`git diff docs/wiki`）が運用の要。LLM が要約するため機密が入りにくい |
| `docs/raw/` | **しない**（README のみ） | 加工前の生資料。キーや個人情報が混ざりやすく、履歴から消せない |

### 「追跡する」と「公開する」は違うのでは？

その通りです。**private リポジトリなら追跡しても外には出ません。**

ただし raw を追跡しない方針を勧めるのは、**public にするかどうかを後から決められるようにするため**です。一度コミットしたものは `git rm` しても履歴に残り、`git filter-repo` + force push + キー再発行が必要になります。「後から消せる」前提で設計しないでください。

### すでに raw をコミットしてしまいました

まず**キーが含まれているかを確認**してください。

```sh
git grep -niE 'sk-ant-|sk-[A-Za-z0-9]{32,}|gh[pousr]_|AKIA[0-9A-Z]{16}|PRIVATE KEY' $(git rev-list --all)
```

- **含まれていない** → `git rm --cached` で追跡を外し、`.gitignore` に追加すれば十分です。履歴に残るのは無害な文書だけです
- **含まれている** → **鍵を再発行してください。**これが最優先です。履歴の書き換えは二次的な作業で、鍵が生きている限り意味がありません

### pre-commit フックは何をしますか？

コミット前に、ステージした**追加行のみ**を検査します。

- `.env` ファイル本体の混入
- Anthropic / OpenAI / GitHub / AWS / Fly のトークン形式
- 秘密鍵（`-----BEGIN ... PRIVATE KEY-----`）

`gitleaks` がインストールされていればそちらに委譲し、無ければ内蔵のパターン検査にフォールバックします。`KEY=...`、`${{ secrets.* }}`、`<your-token>`、`$MY_SECRET` のようなプレースホルダは誤検知しません。

誤検知でどうしても通したいときは `git commit --no-verify` です。

### クローンした人もフックは有効になりますか？

**なりません。** git はセキュリティ上、フックの設定を自動では引き継ぎません。クローン後に1回だけ実行が必要です。

```sh
git config core.hooksPath .githooks
```

生成される `CLAUDE.md` にこの手順が書かれるので、Claude Code が読んで案内してくれます。

> **llm-wiki リポジトリ自身を clone した場合は `githooks`（ドットなし）です。**
>
> ```sh
> git config core.hooksPath githooks
> ```
>
> ここはフックの配布元で `githooks/pre-commit` が実体のため、`--connect` は `.githooks/` へ複製せず元のディレクトリを直接指します。同じファイルを2箇所で保守しないためです。接続先のプロジェクトでは上記のとおり `.githooks` になります。

## Windows

### Windows でも使えますか？

使えます。インストーラの PowerShell 版を実行してください。

```powershell
powershell -ExecutionPolicy Bypass -File .\install\install.ps1
```

macOS / Linux 版との違いは3点だけです。

| 箇所 | Windows での扱い |
|---|---|
| フック | `.ps1` を使い、settings.json に `"shell": "powershell"` が付く |
| `mounts/` | シンボリックリンクではなく**ジャンクション** |
| vault の場所 | `%USERPROFILE%\wiki` |

Wiki の中身（Markdown）は完全に共通なので、Mac と Windows で同じリポジトリを共有できます。

### なぜシンボリックリンクではなくジャンクションなのですか？

Windows のシンボリックリンク作成には**管理者権限か開発者モード**が必要ですが、ディレクトリのジャンクションは通常の権限で作れるためです。Claude Code や Obsidian から見た挙動は同じです。

```powershell
New-Item -ItemType Junction -Path "$env:USERPROFILE\wiki\mounts\myproject" -Target "C:\path\to\myproject\docs\wiki"
```

### PowerShell で日本語が文字化けします

PowerShell 5.1 の出力エンコーディングが原因です。**PowerShell 7 (pwsh) の使用を推奨**します。

同梱のフックスクリプトは先頭で `[Console]::OutputEncoding` を UTF-8 に固定しているため、5.1 でも動作するようにしてありますが、7 のほうが確実です。

### 実行ポリシーでスクリプトが止まります

一時的にバイパスして実行してください。システム設定は変更されません。

```powershell
powershell -ExecutionPolicy Bypass -File .\install\install.ps1
```

### pre-commit フックは Windows でも動きますか？

動きます。`#!/bin/bash` のシェルスクリプトですが、**Git for Windows に bash が同梱**されているためです。PowerShell 版は不要です。

### Git Bash を使っています

`.sh` 版がそのまま動きます。ただし settings.json のフック登録は `bash ~/.claude/hooks/llm-wiki-context.sh` にしてください。

### Mac と Windows で同じ Wiki を共有できますか？

できます。Wiki は素の Markdown なので OS 依存はありません。

注意点は**改行コード**です。このリポジトリには `.gitattributes` を同梱しており、`.sh` は LF、`.ps1` は CRLF に固定されます。Wiki のリポジトリを自分で作る場合も、`* text=auto eol=lf` を入れておくと差分が改行コードで汚れません。

## チーム利用

### チームで共有できますか？

できます。Wiki はただの git リポジトリなので、共有リポジトリに push するだけです。ただし3点の対策が必要です。

1. **衝突対策** — 1回の取り込みで多数のページが変わるため、並行作業すると衝突する。**取り込み実行者を1人（または CI）に固定**し、他の人は `raw/` に資料を積むだけにするのが最も安定
2. **品質対策** — 誤りが全員に伝播する。**AI の書き込みを直接 main に入れず、必ず PR レビューを通す**
3. **スコープ分離** — 個人的な好みとチームの決定を分ける。frontmatter の `scope: shared | private` を使う

### 非エンジニアにも見せたいです

`~/wiki` を独立したリポジトリにし、**MkDocs や Quartz で静的サイト化**して公開する方法があります。エンジニアは Obsidian やエディタで、それ以外の人はブラウザで読めます。

### 権限を分けたいです

**リポジトリ単位でしか分けられません。**機密度が違う知識は、最初からリポジトリを分けてください。
