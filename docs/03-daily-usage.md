# 3. 日々の使い方

覚えるコマンドは**4つだけ**です。

| いつ | コマンド | 目安 | 人の判断 |
|---|---|---|---|
| 作業を始めるとき | `/llm-wiki query 今の状況と次にやることは？` | 10秒 | なし |
| 作業の区切り | `/llm-wiki ingest 今日の作業内容` | 5〜10分 | あり |
| ingest の直後 | `git diff docs/wiki` | 5分 | **あり（重要）** |
| 週1回 | `/llm-wiki lint` | 15〜30分 | **あり（重要）** |

---

## 1日の流れ（例）

```
09:30  /llm-wiki query 今の状況と次にやることは？
       → 「オフライン同期の競合解決が未着手。優先度2はリトライ処理のエラー分類」

09:35  コードを書く（Wiki は触らない）

12:00  ...

17:00  /llm-wiki ingest 今日の作業内容
       → raw に固定 → 4ページが書き換わる

17:10  git diff docs/wiki
       → 差分を読んで1箇所指摘、修正させる

17:20  終了
```

Wiki を意識するのは**朝と夕方の数分だけ**です。作業中は普通にコードを書きます。

---

## query — 聞く

```
/llm-wiki query 今の状況と次にやることは？
/llm-wiki query オフライン同期が競合するのはなぜ？
/llm-wiki query デプロイ手順を教えて
```

`index.md` から関連ページを辿って答えます。コードベースの探索が走らないので数秒で返ります。

### 良い回答の見分け方

**回答にページ名の引用があること。**

> 良い例:「`taskflow-open-issues.md` によると、優先度1は複数端末での競合解決の検証です」
>
> 悪い例:「オフライン同期の検証が残っているようです」← Wiki を読んでいない可能性

引用が無ければ「`index.md` から読んで」と指示し直してください。

### Wiki に答えが無いとき

「Wiki に無い」と明言してから調べるのが正しい動作です。**推測で埋めさせないでください。**それが書き戻されると、以後ずっと嘘を答え続けます。

調べた結果に再利用価値があれば、ページとして書き戻すよう提案させます。

## ingest — 取り込む

```
/llm-wiki ingest 今日の作業内容
/llm-wiki ingest docs/raw/2026-08-14-stripe-docs.md
/llm-wiki ingest https://example.com/article
```

会話の内容を取り込む場合、AI はまず `docs/raw/YYYY-MM-DD-topic.md` として**固定**してから取り込みます。後から出典を辿れるようにするためです。

**`raw/` に置いたファイルは以後書き換えません。**内容が変わったら、新しい日付のファイルとして追加します。

### 人間の仕事: 何を入れないか決める

ここで質が決まります。

- **会話ログを丸ごと入れる** → 試行錯誤の過程まで載って薄まる
- **結論だけ入れる** → なぜそうしたかが消えて、後から判断できなくなる

判断基準は「**次に同じ場面に来た人が踏む罠かどうか**」です。

> **実例**
> `fly launch` で失敗して `apps create` に切り替えた経緯は、結果だけ書くと次の人がまた `fly launch` を使って同じ罠を踏みます。だから**過程ごと**残しました。

### 正常に取り込めているサイン

**1つの資料で複数のページが書き換わります。** 1ページしか触っていなければ取り込みが浅いので、こう指示します。

```
既存ページとの関連をもっと洗って。関係するページを全部更新して
```

### いつ ingest するか

毎回でなくて構いません。**セッションの終わりに1回**、あるいは**週の終わりに「今週の決定事項」だけ**でも十分機能します。取り込みすぎると薄まるので、少なめから始めてください。

## git diff — レビューする

```sh
git diff docs/wiki
```

**この運用でいちばん重要な工程です。**詳しくは [4. レビューと lint](04-review-and-lint.md) を読んでください。見るのは3点だけです。

1. **訂正は妥当か** — 古い記述を上書きした箇所
2. **確度の表記は正しいか** — 未検証を断定していないか
3. **機密が混ざっていないか** — API キー、アカウント情報

指摘はその場で口頭で構いません。

```
taskflow-deployment.md のオフライン同期の記述、実機未確認だから confidence: low にして
```

---

## lint — 点検する

```
/llm-wiki lint
```

週1回、曜日を決めて回します。**検出結果を報告するだけで、勝手には直しません。**直すものを人間が選びます。

```
矛盾1と3を直して。リンク切れは taskflow-session-recovery だけ書いて
```

これも [4. レビューと lint](04-review-and-lint.md) で詳しく説明します。

---

## やりがちな失敗

| 失敗 | 何が起きるか |
|---|---|
| **lint を回さない** | 数ヶ月で「古いメモ置き場」に劣化する。最も多い失敗 |
| **差分レビューを飛ばす** | 誤りが定着し、以後ずっと同じ誤りを自信満々に答える |
| **全プロジェクトに一度に導入する** | 規約が自分に合っているか検証する前に構造が固定される |
| **何でも取り込む** | 重要な記述が雑多な情報に埋もれる |
| **API キーを書かせる** | 「`.env` に設定済み」とだけ書かせる |
