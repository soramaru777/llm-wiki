# 1. LLM Wiki とは

## ひとことで

**AI に司書をやらせて、知識を腐らせずに積み上げる仕組み**です。

読んだ資料や決めたことを AI が Markdown のページとして書き、相互にリンクを張り、新しい情報が来たら**古い記述を書き換えて**維持し続けます。

2026年4月に Andrej Karpathy（OpenAI 共同創業メンバー、元 Tesla AI ディレクター）が GitHub Gist で公開した設計パターンです。製品ではなく**考え方**なので、実装は各自で組みます。

---

## 何が起きるのか

### 従来: 毎回ゼロから読ませる

```
あなた「TaskFlow の今の課題は？」
  ↓
AI: コードを探索 → README を読む → ソースを追う → 答える
  ↓
（30秒待つ。毎回同じことを繰り返す。毎回課金される）
```

### LLM Wiki

```
[取り込み] 資料や会話を ingest すると、AI が Wiki を書く（ここが重い・1回だけ）
  ↓
あなた「TaskFlow の今の課題は？」
  ↓
AI: index.md → taskflow-open-issues.md を読む → 答える
  ↓
（3秒。「taskflow-open-issues.md より」と根拠を示す）
```

**重い処理を、質問のたびから取り込みの1回に移す。**これが本質です。

---

## 3つの操作

覚えるのはこれだけです。

| 操作 | 何をするか |
|---|---|
| **ingest** | 資料を取り込み、関連するページをまとめて書き換える |
| **query** | Wiki を読んで質問に答える。根拠のページ名を必ず示す |
| **lint** | 矛盾・古い記述・孤立したページを点検する |

---

## 3層の構造

```
raw/     生の資料。一度置いたら書き換えない
  ↓ ingest
wiki/    AI が書いて維持する Markdown ページ群
  ↑ 規約
SCHEMA   ページの書き方・命名・置き場所のルール
```

`raw/` を残しておくことで、後から「この記述の出典は何だったか」を辿れます。

---

## 普通のメモとの違い

**メモは追記されるだけですが、Wiki は書き換えられます。**

これが決定的な差です。実例を挙げます。

最初の取り込みで、デプロイ手順に `fly launch --no-deploy` と書かれました。次のセッションで実際にやってみると、`fly launch` は作り込んだ設定ファイルを勝手に書き換えることが分かりました。

- **メモなら** → 新しいメモが増え、古いメモも残る。どちらが正しいか後で分からない
- **Wiki なら** → 該当ページが `apps create` + `deploy` に**書き換わり**、なぜ変えたのか理由が添えられる

メモは古びますが、Wiki は更新されます。

---

## RAG との違い

RAG（検索拡張生成）は、質問のたびに資料をベクトル検索して関連部分を引っぱってくる仕組みです。

| | RAG | LLM Wiki |
|---|---|---|
| いつ処理するか | 質問のたび | **取り込み時に1回** |
| 中身 | ベクトル化されたチャンク（人は読めない） | **Markdown（人が読める）** |
| 間違いの直し方 | 元文書を直す。次に検索に当たるかは運 | **該当ページを直せば確定で直る** |
| 必要なもの | 埋め込みモデル、ベクトルDB | **テキストエディタだけ** |
| 得意な規模 | 数百万件 | 数百〜数万件 |
| 終わったら残るもの | 何も残らない | **人が読めるドキュメント** |

比喩で言うと、**RAG は「倉庫から都度取り出す」、LLM Wiki は「司書が整理し続ける図書館を読む」**です。

どちらが優れているという話ではありません。大量の文書から都度1件を探すなら RAG、同じ対象に何度も聞くなら Wiki です。

---

## 使っていて何が違うか

### 質問のハードルが下がる

「今の課題って何だっけ」に3秒で返るなら気軽に聞けますが、毎回30秒コードを探索されるなら聞かなくなります。この差が、実際の使用回数を大きく変えます。

### 答えを疑う代わりに、答えを直せる

回答に「`taskflow-open-issues.md` より」と根拠が付くので、**そのファイルを開いて自分で直せます**。直せば次回から確実にその答えになります。

「AI の答えを信じるかどうか」から「自分がレビューしたページを AI が読んでいる」に変わる、というのが体感上いちばん大きい違いです。

### 失敗の仕方が変わる（重要）

- RAG は**毎回違う失敗**をします。運が悪いと外す。再現しないので直せない
- LLM Wiki は**毎回同じ失敗**をします。誤りが書き込まれると自信満々に繰り返す

一見 Wiki のほうが怖いのですが、**固定されている＝見つけられるし、直せば二度と起きない**。だから [lint とレビュー](04-review-and-lint.md) が必須なのです。

### ドキュメントが副産物として残る

使うほど、人に渡せる資料が育ちます。「知識ベースを作る」と「ドキュメントを書く」が別作業ではなくなります。

## 代わりに発生する仕事

正直に書きます。**放り込むだけで済む仕組みではありません。**

- 何を入れるか選ぶ（入れすぎると薄まる）
- 取り込み結果をレビューする
- 週1回 lint して、矛盾を裁定する

**週30〜60分**が目安です。役割が「検索する人」から「編集長」に変わります。楽になるのは質問するときで、貯めるときはむしろ手間が増える。この非対称性を受け入れられるかが、続くかどうかの分かれ目です。

詳しくは [4. レビューと lint](04-review-and-lint.md) を読んでください。
