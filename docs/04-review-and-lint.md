# 4. レビューと lint

**この章が LLM Wiki のいちばん大事な部分です。**

前章までのコマンドは AI がやってくれますが、ここだけは人間がやります。逆に言えば、**ここをやらないなら LLM Wiki を導入する意味がありません**。

---

## なぜ人間が要るのか

LLM Wiki は**誤りを固定する**仕組みだからです。

RAG は毎回違う失敗をしますが、Wiki は一度誤りが書き込まれると**毎回まったく同じ誤りを、自信満々に答え続けます**。しかも根拠のページ名まで添えて答えるので、もっともらしく見えます。

これは弱点であると同時に利点でもあります。**固定されているから見つけられるし、直せば二度と起きない。**その「見つける」工程がレビューと lint です。

---

## ingest 直後のレビュー

```sh
git diff docs/wiki
```

差分を上から読みます。**見るのは3点だけ**で、文章の巧拙は見なくて構いません。

### 1. 訂正は妥当か

古い記述を上書きした箇所を探します。

AI は「新しい情報が来た＝上書き」と機械的に判断します。しかし本当は、

- 前の記述が**誤っていた**のか
- 単に**状況が違う**だけなのか（環境、バージョン、前提条件）

を区別する必要があります。ここを素通しすると、**「最後に喋った人が勝つ」だけの Wiki** になります。

> **実例**
> デプロイ手順が `fly launch --no-deploy` から `apps create` + `deploy` に書き換わっていました。理由は「`fly launch` は作り込んだ設定ファイルを書き換えることがあるため」。これは前の記述が実際に誤りだったので、訂正として妥当と判断しました。

### 2. 確度の表記は正しいか

**LLM は放っておくと、未検証のことも断定調で書きます。**

次の3つを区別してください。

| 実態 | 書かせ方 |
|---|---|
| 実機・実測で確認した | 断定してよい（`confidence: high`） |
| 仕様上そうなるはず | 「仕様上は」と明記（`confidence: medium`） |
| たぶんそう | `confidence: low` + 本文にも「未検証」と書く |

ここを怠ると、**半年後の自分が「Wiki に書いてあるから確認済みだ」と誤解します**。これが実害としては一番大きい。

> **実例**
> 話者分離のページに `confidence: low — 複数話者での精度は未確認` を付けました。単独話者で表示までは確認しましたが、肝心の分離精度は試せていないためです。

### 3. 機密が混ざっていないか

AI は親切心で全部書こうとします。毎回止めてください。

- API キー、トークン、パスワード → 「`.env` に設定済み」とだけ書かせる
- アカウントの使い分け、認証情報
- git 未追跡ファイル（`docs/local/` など）の内容 → **参照先として名前を挙げるに留める**

### 指摘の仕方

その場で口頭で構いません。

```
termlens-deployment.md の話者分離の記述、実機未確認だから confidence: low にして
```

```
knowledge/fly-io-deployment.md にアカウント名が入ってる。消して
```

## 週1回の lint

```
/llm-wiki lint
```

**lint は検出を報告するだけで、自動修正しません。**これは意図的な設計です。修正の判断こそが人間の仕事だからです。

### 検出項目と、人間が決めること

| 検出項目 | 何が出るか | あなたが決めること |
|---|---|---|
| **矛盾** | 同じ事実を違うふうに書いている2ページ | どちらが正しいか。任せると機械的に新しい方を採る |
| **リンク切れ** | 存在しないページへの `[[リンク]]` | **これは「次に書くべきページ」の候補**。全部書かず、価値があるものだけ選ぶ |
| **孤立ページ** | どこからもリンクされていないページ | リンクを張るか、そもそも不要なので消すか |
| **陳腐化** | 更新日が古く、元資料が変わっているページ | 更新するか、「もう触らない」と決めて閉じるか |
| **出典なし** | `sources` が空のページ | 出典を補うか、記述ごと削るか |
| **昇格候補** | 複数プロジェクトで重複している知識 | プロジェクト固有か、`~/wiki/knowledge/` に上げるか |

### リンク切れは「エラー」ではない

ここは誤解しやすい点です。

存在しないページへリンクを張るのは**意図的に許されています**。「このページはまだ無いが、いずれ要る」という印になるからです。lint はそれを一覧で出してくれるので、**書くべきページのリスト**として使います。

全部書く必要はありません。要らないものはリンクごと消します。

### 指示の仕方

一括で構いません。

```
矛盾1と3を直して。リンク切れは termlens-session-recovery だけ書いて。
孤立ページの termlens-old-plan は消して
```

修正後、`log.md` に記録が追記されていることを確認してください。

## 人間とAIの分担

線引きを整理するとこうなります。

### 人間にしかできない4つ

いずれも「**正解が資料の中にない**」判断です。

1. **何を入れないか** — 入力の選別
2. **どちらが正しいか** — 矛盾の裁定
3. **どこまで確かか** — 確度の格付け
4. **何を書かないか** — 機密の線引き

### AI に任せてよいこと

- 資料の要約とページ化
- 関連ページへのリンク張り
- 規約に沿った整形（frontmatter、命名）
- 矛盾・孤立・リンク切れの**検出**（判断ではなく検出）

## 負荷を下げる

週30〜60分が目安ですが、重ければ次の手があります。

| 打ち手 | 効果 |
|---|---|
| lint を週次 cron / GitHub Actions に載せ、結果を Issue にする | 実行忘れがなくなる |
| **入れるソースを絞る** | 週1回、「今週の決定事項」だけでも機能する。まずこれ |
| `SCHEMA.md` をテンプレとして効かせる | 毎回「どう書く？」を考えない |
| チームでは ingest 実行者を1人（または CI）に固定 | 他の人は `raw/` に積むだけ。品質が安定し、衝突も減る |

**いちばん効くのは「入れるソースを絞る」**です。負荷は取り込み量にほぼ比例します。

---

## チームで使う場合

Wiki はただの git リポジトリなので、共有リポジトリに push すれば共有できます。ただし個人利用から素直にスケールしない点が3つあります。

1. **衝突が多い** — 1回の取り込みで多数のページが変わるため、並行作業すると衝突だらけになる。→ **ingest 実行者を1人に固定**するのが最も安定
2. **誤りが全員に伝播する** — 個人なら自分が損するだけだが、チームでは全員の判断を汚染する。→ **PR レビューを必ず通す**。AI の書き込みを直接 main に入れない
3. **個人の知識と共有知識が混ざる** — 「自分の作業の好み」と「チームの設計判断」は分ける。→ frontmatter に `scope: shared | private` を持たせる
